# Отчёт по практической №1
Развертывание локального Lakehouse, ELT-преобразование и бенчмарк форматов/сжатия
## 1. Вариант и масштаб

| Поле | Значение |
|---|---|
| ФИО (как в VK Education) | Глазунова Полина Ильинична|
| Вариант (запрос) | Q3 |
| Масштаб `sfN` | sf5 |
| Почему выбрал такой масштаб |Я выбрала масштаб sf5 (который примерно даёт 30 млн строк в `lineitem`). Потому что этого объема достаточно, чтобы увидеть разницу в сжатии и времени выполнения запросов, и при этом он нормально работает на 16 ГБ оперативной памяти и не займёт всё свободное место на моем ноутбуке (в отличие от sf10, который требует значительно больших ресурсов). |

## 2. Поднятые сервисы — и почему именно они

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | Бесплатный S3-совместимый сервис, легко разворачивается в Docker (я использовала форк pgsty/silo, так как оригинальный MinIO теперь требует лицензию).|
| PostgreSQL | БД, где Lakekeeper хранит метаданные каталога | Надежная реляционная СУБД, нативно поддерживается Lakekeeper для хранения служебных данных.|
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Реализует стандартный REST-каталог для Iceberg. Позволяет отделить метаданные от файлов данных и удобно управлять ими.|
| Trino | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | Выбор пал на Trino, а не на Spark, так как Trino - это быстрый распределенный движок для ad-hoc аналитики и он идеально подходит для быстрых запросов к объектному хранилищу через коннектор Iceberg.|
| (BI: Superset / Metabase) | отчёт/дашборд поверх Gold |  Легкий в запуске BI-инструмент с открытым исходным кодом. Имеет встроенный драйвер для Trino и позволяет строить графики без написания кода.|


### Скрипты, которыми поднимал стек

```bash
# MinIO (объектное хранилище)
docker run -d --name lakehouse-minio -p 9000:9000 -p 9001:9001 -e MINIO_ROOT_USER=minioadmin -e MINIO_ROOT_PASSWORD=minioadmin -v minio-data:/data pgsty/silo:latest server /data --console-address ":9001"

# PostgreSQL (база для Lakekeeper)
docker run -d --name lakehouse-pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 -v pg-data:/var/lib/postgresql/data postgres:17

# Trino (SQL-движок)
docker run -d --name trino -p 8080:8080 -v "${PWD}\catalog:/etc/trino/catalog" trinodb/trino:476

# Metabase (BI)
docker run -d --name metabase -p 3000:3000 metabase/metabase:latest
```

## 3. Разбор запроса — какие данные нужны

Какие таблицы и колонки TPC-H реально нужны твоему запросу.

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
|customer |custkey, mktsegment | Фильтр (mktsegment = 'BUILDING') и джойн с orders по custkey|
|orders |orderkey, custkey, orderdate, shippriority |Фильтр по дате (orderdate < 1995-03-15), джойн с customer и lineitem. Вывод orderdate и shippriority. |
|lineitem |orderkey, extendedprice, discount, shipdate |Фильтр по дате (shipdate > 1995-03-15), джойн по orderkey. Вычисление выручки (extendedprice * (1 - discount)) и агрегат sum(). |

### Gold (витрина)

| Таблица | Колонки | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|
| gold_top_orders | orderkey, orderdate, shippriority, revenue | 10 | 0,0008 | PARQUET | ZSTD | нет | Агрегированный ответ на запрос. 10 строк не требуют оптимизации хранения |

Для всех слоев был выбран **PARQUET**, так как это колоночный формат, являющийся стандартом де-факто в экосистеме Lakehouse. В отличие от ORC, Parquet обеспечивает высочайшую степень сжатия и скорость аналитических запросов за счет чтения только нужных колонок.
Партиционирование не использовалось, так как на моем масштабе это не имеет смысла.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ  |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? |Обычные БД дорого масштабировать на десятки терабайт, а обычный Data Lake (просто файлы в S3) не поддерживает транзакции и ACID. Lakehouse решает обе проблемы: дешевое объектное хранилище (S3) плюс табличный формат (Iceberg), который добавляет метаданные, поддержку схем, откаты (time travel) и позволяет делать SQL-запросы через движки вроде Trino. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? |При добавлении колонки (ALTER TABLE ADD COLUMN) Iceberg просто обновляет метаданные. Старые parquet-файлы не перезаписываются, при чтении в новой колонке для старых строк возвращается NULL. Это позволяет менять схему без простоя и переливки терабайт данных. |
| Пример скрипта восстановления данных из снапшота (time travel) |ALTER TABLE lakekeeper.lakehouse.silver_order_lines EXECUTE rollback_to_snapshot(5429817954332802307); (ID снапшота был взят из системной таблицы $snapshots). Этот запрос мгновенно откатывает состояние таблицы к предыдущей версии без перезаписи файлов. |

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| Metabase (BI) | Открытый, бесплатный BI-инструмент, легко запускается одной docker-командой и имеет понятный интерфейс и встроенный Trino-коннектор. В отличие от Superset, не требует поднятия отдельной базы для метаданных. |
|Trino (движок)|В отличие от batch-движков (Spark), Trino предназначен для интерактивных запросов с низкой задержкой. Ему не нужно поднимать тяжелый SparkContext на каждый запрос, что делает его идеальным для BI-систем.|

Действия в UI:
1. Подключилась к Trino (Host: host.docker.internal, Port: 8080, Database: lakekeeper, User: trino).
2. Перешла в Native Query. Чтобы обойти проблему парсинга длинных имен, использовала переменную `{{table}}`.
3. В настройках переменной выбрала тип «Таблица» и указала на **`bronze_customer_zstd`**.
4. Так как слой Bronze содержит 750 000 сырых строк, я добавила оператор `LIMIT 100`. Это предотвращает падение браузера и перегрузку RAM при предпросмотре.
5. Metabase успешно отобразил сырые данные из Бронзового слоя напрямую из MinIO (через Trino).

## 7. Выводы

В ходе работы я поняла, что медальон (Bronze -> Silver -> Gold) — это эффективный способ организации данных, который разграничивает зоны ответственности: он позволяет хранить сырые данные отдельно от очищенных и агрегированных. Выбранное хранение в формате Lakehouse (Iceberg поверх S3) оказалось лучше классической реляционной БД, так как легко масштабируется, поддерживает ACID-транзакции и Time Travel. При сравнении кодеков я выяснила, что ZSTD сжал данные сильнее, чем GZIP, и выполнил тестовый запрос на 2,5 секунды быстрее. Использование легковесных Trino и Metabase вместо других альтернатив позволило бесплатно и быстро развернуть интерактивный стек для аналитики в вебе.
